## 范围与证据边界

用户已明确：目标是个人全部知识，包括生活、学习、阅读、工作、兴趣、经历、长期思考。当前量化项目只是组成部分，不能把现有项目目录扩大成整个人生的分类框架。

本次分三路并行调研：官方能力与可靠性、知识管理方法、GitHub 示例与生态。主任务另核查常见插件及跨工具边界。未安装软件或插件、未操作用户 vault、未迁移项目文件；本文件仅遵守仓库的研究记录约定。

官方文档用于确认功能和限制；方法作者文章用于理解设计意图；GitHub README 和示例文件用于观察可复用做法。这些不是不同方法的受控效果实验，不能证明一种方法对所有人效率最高。未用 star 数量证明有效，也没有把 README 存在视为已经实际运行验证。插件与发布工具的状态在未来可能变化，启用前仍应查当前文档。

## 建议优先采用的实践

1. **以一个个人主库起步。** 阅读、生活、兴趣与长期思考经常相互关联。仅在组织权限、保密、共享边界确有区别时考虑分库；分库本身不是安全隔离。官方说明内部链接以 vault 为范围，且不建议 vault 嵌套。[数据存储](https://obsidian.md/help/data-storage)
2. **文件夹管理笔记角色和生命周期，链接表达主题关系。** 一条笔记可以连接多个问题，无需在“心理学／职业／家庭”等多个目录复制。不要先造一棵覆盖所有学科的深层树；已有自然的少量主题文件夹也可保留。
3. **区分来源材料、自己的理解、当时经历。** 三者可以在同一文件中用明确段落区分；材料变多、需要跨处复用时再拆成独立笔记。无需为每条剪藏强制创建多份文件。
4. **值得反复使用的观点保留证据与反例。** 记录当前判断、适用条件、来源、反例、未知之处和修订日期。个人感受可以保留为个人观察，不能自动提升为普遍规律。
5. **链接旁写清关系。** 例如“这个案例支持……，但与……在约束上不同”。不用给每篇笔记设定必须有多少链接的配额；没有链接的收据或日记也未必需要修复。
6. **先靠标题、搜索和少量入口找东西。** 概念笔记可用清楚的论点或问题命名；日记用日期；书籍和人物用名称。跨语言、缩写或别称用 `aliases`，避免同义概念重复建档。[Aliases](https://obsidian.md/help/aliases)
7. **属性只服务于真实检索。** 初期可用 `type`、`created`；来源类增加 `source`，需要工作流时才用 `status`。同名属性维持统一类型；不是所有笔记都必须填表。[Properties](https://obsidian.md/help/properties)
8. **按使用需要逐步提炼。** 捕捉时写一句“为何保存／以后何时可能用到”。每次重新使用时补充理解；不要求所有旧资料都整理完才开始新库。
9. **轻量回顾，留下反馈。** 可先每周处理一次收件箱，选择最有关联的材料更新；允许直接删除无价值剪藏，也允许归档长期未读但有档案意义的材料。回顾频率是试用建议，不是研究证明的最佳周期。
10. **评价实际帮助。** 观察能否重新找回上下文、解释一个问题、修正判断、支持决定或创作。笔记数、图谱大小、插件数只能反映规模，不能单独证明知识质量。

## 可试用的结构

这是待用户后续选择的建议，没有实际创建个人 vault。文件夹名称和数量可按使用习惯简化。

```text
个人知识库/
  Home.md             # 当前关心的问题、常用入口
  00 收件箱/           # 随手记、待处理材料
  10 日志/             # 日常经历、案例、周月回顾
  20 项目/             # 有结束条件的生活或工作事项
  30 领域/             # 健康、家庭、职业等长期责任入口
  40 资料/             # 书籍、文章、课程、人物等来源
  50 知识/             # 自己的概念、论点、方法与问题地图
  90 归档/             # 已完成或不活跃的项目与材料
  99 系统/             # 附件、模板、个人使用约定
```

“领域”主要回答我长期关心和负责什么；“知识”回答我对某个问题如何理解。领域页和问题地图都只是普通笔记，可以指向同一条知识，不产生副本。若用户更喜欢少目录，也可以合并领域和知识，靠入口和属性区分。

例如一本沟通类书籍保留来源笔记；一次困难沟通写在日志中；“给建议前先确认对方希望获得何种帮助”作为待检验的个人判断，连接书籍和案例；“关系与沟通”地图汇集相关问题。该判断是演示标题，不是本次核实的普遍心理学结论。

## 两个最值得准备的轻模板

普通随手记不要求套模板。下面模板仅用于值得长期发展的内容。

**知识／判断笔记：**

```markdown
# 我正在理解的一个问题或论点

当前理解：用自己的话说明。
依据：来源、页码或原始案例。
边界与反例：何时可能不成立？
相关认识：它支持、修正或反对哪些已有笔记？
仍不确定：还缺什么证据？
修订：日期、改变了什么、为什么改变。
```

**案例／经验记录：**

```markdown
# 日期与事件

当时情境和约束：
我观察到的线索：
当时的判断与预期：
其他选择和不确定性：
采取的行动：
后来实际发生了什么：
哪些线索有用，哪些误导：
下次遇到什么条件时重新考虑：
```

这类记录适用于工作选择、沟通、旅行、摄影练习等，也可以用于项目研究。它能保留默会判断的线索与反馈，无法将所有经验完整语言化，更不能代替亲身练习。需要保留“当时”的判断，避免结果出现后改写成自己早已知道。

## 原生能力和插件的选择顺序

官方 [Bases](https://obsidian.md/help/bases) 已提供基于笔记及属性的视图，定义可保存为 `.base`，数据仍在本地 Markdown。初学者不必再把 Dataview 当成“建立书单或项目表”的必需前提。Bases 也不是所有 Dataview 查询的等价替代。

| 需求 | 优先做法 | 出现明确需求后再考虑 |
| --- | --- | --- |
| 查找、阅读与关联 | 原生搜索、Quick switcher、Backlinks、链接 | 不因别人装了搜索插件就安装 |
| 普通模板和日志 | Templates、Daily notes，按需启用 | [Templater](https://github.com/SilentVoid13/Templater)：变量、脚本和复杂模板 |
| 统一捕捉入口 | 固定收件箱或日志 | [QuickAdd](https://github.com/chhoumann/quickadd)：反复使用的捕捉／建档步骤 |
| 书单、课程和项目视图 | Properties + Bases | [Dataview](https://github.com/blacksmithgu/obsidian-dataview)：原生无法满足的查询与计算 |
| 跨笔记待办 | 简单 Markdown 任务或继续用已有任务工具 | [Tasks](https://github.com/obsidian-tasks-group/obsidian-tasks)：跨文件聚合、周期任务；无需强迫搬走已好用的日历和提醒工具 |
| 桌面版本追溯 | 独立备份；按技术熟悉程度使用 Git | [Obsidian Git](https://github.com/Vinzent03/obsidian-git)：自动提交和差异；README 明确提示移动端不稳定，不把它作为手机默认同步方案 |

插件应解决一个实际、重复出现的问题，安装一个后观察是否真的减少工作。Templater 可运行代码／系统命令，DataviewJS 也有文件和网络能力；官方说明社区插件没有可靠的细粒度权限隔离。因此复制完整 vault 的同时启用所有脚本，存在额外信任成本。[插件安全](https://obsidian.md/help/plugin-security)

需要大量论文与文献引用时，可让 [Zotero](https://www.zotero.org/support/quick_start_guide) 管原文和文献条目，Obsidian 管自己的思考并引用来源。需要准确记忆的知识可另外采用主动回忆／间隔复习；本文不评估具体记忆训练效果，也不建议把所有知识笔记做成记忆卡。

## 同步、备份、可迁移性

- **同步只选一条主路线。** Apple 设备组合可评估 iCloud；跨平台且希望少维护时可评估官方 Sync。具体选择仍取决于设备、附件规模、预算和网络条件，当前未知，不作绝对推荐。官方提醒同一 vault 避免同时运行多个同步服务，并保持云盘文件在本地可用。[同步指南](https://obsidian.md/help/sync-notes)
- **同步不等于备份。** 选择一台常用设备，将整个 vault（含必要配置与附件）定期单向备份到独立位置，保留历史并尝试恢复。File recovery 只是有限、每设备的恢复机制。[备份指南](https://obsidian.md/help/backup)
- **冲突和加密各有边界。** Markdown 自动合并仍可能产生重复；Canvas 等其他类型按最后修改覆盖，可逐设备选择创建冲突文件。官方 Sync 默认端到端加密并不会使本机 vault 自动加密。[冲突说明](https://obsidian.md/help/sync/troubleshoot)、[安全说明](https://obsidian.md/help/sync/security)
- **普通文本可迁移，特殊表现未必可迁移。** 关键判断直接写在 Markdown 正文；表格视图、脚本、块引用等须考虑工具依赖。更重视通用编辑器兼容时可用标准 Markdown 链接；日常 Obsidian 使用则可选 Wikilinks。文件重命名优先在 Obsidian 中进行，让其更新链接。[内部链接](https://obsidian.md/help/links)
- **个人隐私与公开内容分别决定。** 公开博客不是私人库的必需阶段。使用 AI 时核对数据实际发送位置；官方 Clipper 的 Interpreter 会将页面上下文发给所选模型，远程模型与本地模型的处理边界不同。[Interpreter](https://obsidian.md/help/web-clipper/interpreter)

## AI 的合理角色

综合建议：让 AI 辅助找已有资料、提出潜在关联、发现矛盾、整理候选摘要；保留来源位置，让用户确认自己的观点。AI 草稿与已确认的个人理解应有明确标记，不直接批量覆盖旧笔记。外部网页、原文引述和 AI 推断应可区分。

检索到的相关内容不等于支持结论。尤其应要求回答指出“不确定、缺证据、与哪些笔记冲突”，并保留人工纠正。当前没有用户语料和检索效果评估，不能宣称接入 AI 后即可得到可靠的个人问答系统。

## 当前项目如何作为个人知识的一部分

个人主库应位于独立于单个代码仓库的长期位置。为当前项目保留一篇项目入口，说明研究目标、关键决策、经验和回到原始证据的路径；代码、配置、原始数据和完整 stage 仍在现有仓库中维护。

从项目中提炼的跨领域认识可以进入个人知识层，例如如何区分证据与愿望、如何保留失败假设、何时停止无效探索；这些只是示例问题，不是对策略收益的结论。提炼笔记链接回证据，项目不应成为两个可分别编辑的事实副本。

若以后需要跨设备访问项目结论，可导出带来源和日期的摘要快照。不要默认整仓同步到手机，也不要依靠 symlink 拼接多个库；官方明确提醒符号链接存在数据与同步风险。[符号链接说明](https://obsidian.md/help/symlinks)

## 建议的四周试用与验收

以下为后续行动建议，本次没有执行：

1. 第 1 周：从当周真实材料开始，至少涵盖阅读、生活经历和工作。确定移动端捕捉方式，建立同步与独立备份；不全量迁移历史资料。
2. 第 2 周：按实际需要形成几篇自己的理解，把相互相关的材料连起来。建立一页个人使用约定，记录标题、日期、属性和存放习惯。
3. 第 3 周：围绕一个真实关心的问题做主题地图，或完成一次生活／工作决定的案例复盘。仅在操作反复造成阻力时加插件。
4. 第 4 周：检查是否能找回旧材料、解释问题、更新认识；评估维护时间与收件箱积压，并试着恢复一份备份。保留有帮助的结构，删减无用步骤。

评价问题：我是否更容易找回当时上下文？哪一条笔记改变了理解或决定？能否明确区分来源和自己的推断？是否出现一周不维护就无法继续使用的结构？这些比追求固定笔记数量更有意义。

## 结论与反思

- 阶段结论：推荐一个覆盖个人生活的主库，以简单文件组织、概念积累、问题入口和案例反馈起步；当前项目通过摘要与证据链接接入。
